### Проблема 1: Сбой C-драйвера NetCDF4 на путях с кириллицей в Windows
* **Симптом:** Ошибка C-библиотеки HDF5 / NetCDF: `[Errno -101] NetCDF: HDF error` или `No such file or directory`.
* **Причина:** C-библиотека NetCDF не поддерживает многобайтовые пути UTF-8 на платформе Windows.
* **Решение:** Преобразование пути в короткий формат Win32 (8.3) через вызов `kernel32.GetShortPathNameW`:
```python
import ctypes
import os
from ctypes import wintypes

def get_short_path(path: str) -> str:
    if os.name == 'nt' and os.path.exists(path):
        _fn = ctypes.windll.kernel32.GetShortPathNameW
        _fn.argtypes = [wintypes.LPCWSTR, wintypes.LPWSTR, wintypes.DWORD]
        _fn.restype = wintypes.DWORD
        buf = ctypes.create_unicode_buffer(0)
        needed = _fn(path, buf, 0)
        if needed > 0:
            buf = ctypes.create_unicode_buffer(needed)
            _fn(path, buf, needed)
            return buf.value
    return path
```

### Проблема 2: Заражение тензоров значениями NaN при маскированной арифметике
* **Симптом:** На итерации алгоритма невязка $\|R\|_F$ принимает значение `nan`, вычисления аварийно прерываются.
* **Причина:** По стандарту IEEE 754 произведение нуля на нечисловое значение дает нечисловое значение: $0.0 \times \text{NaN} = \text{NaN}$. Если входной массив содержит пропуски (`NaN`), любое матричное произведение с маской порождает `NaN`.
* **Решение:** Замена `NaN` на $0.0$ до начала тензорных операций с сохранением отдельной бинарной маски валидности:
```python
D_valid = torch.nan_to_num(D_tensor, nan=0.0)
valid_mask = torch.isfinite(D_tensor).float()

# Пример в итерационном процессе:
residual = (D_valid - L * valid_mask) * valid_mask
```

### Проблема 3: Зависание алгоритмов оптимизации при недостижимом пороге сходимости в float32
* **Симптом:** Число итераций достигает лимита `max_iter`, невязка стабилизируется около значения $8 \times 10^{-7}$.
* **Причина:** Машинный эпсилон одинарной точности IEEE 754 составляет $\epsilon \approx 1.19 \times 10^{-7}$. Погрешности округления при расчете сингулярных чисел делают относительный порог $\|R\|_F / \|D\|_F \le 10^{-7}$ недостижимым.
* **Решение:** Использовать порог сходимости $\text{tol} = 1.0 \times 10^{-5}$ для вычислений в типе `float32`.

### Проблема 4: Переполнение видеопамяти при вычислении SVD на крупномасштабных растрах
* **Симптом:** `torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 14.8 GiB...`
* **Причина:** Точное сингулярное разложение матрицы размера $M \times N$ требует создания унитарных матриц $U \in \mathbb{R}^{M \times M}$ и $V \in \mathbb{R}^{N \times N}$. При размерах свыше $3000 \times 3000$ объем выделяемой памяти превышает 14 ГБ.
* **Решение:** Пространственное блочное разбиение растра на тайлы размером $512 \times 512$ с шагом перемещения $448$ (перекрытие $64$ пикселя). Объем VRAM на один тайл составляет $\le 0.08$ ГБ.

### Проблема 6: Зависание процессов и утечки видеопамяти при пакетной обработке
* **Симптом:** Процесс застревает в памяти, повторные запуски вызывают `CUDA out of memory`.
* **Причина:** Накопление графов автодифференцирования PyTorch в кэше аллокатора CUDA, отсутствие промежуточной очистки мусора.
* **Решение:**
1. Очистка кэша перед запуском вычислений и после каждого крупного блока:
```python
import gc
import torch

gc.collect()
if torch.cuda.is_available():
    torch.cuda.empty_cache()
    torch.cuda.ipc_collect()
```
2. Установка максимального времени выполнения одной задачи не более 20 минут.
3. Логирование прогресса обработки каждые $N$ блоков.

### Проблема 10: Сбой кодировки консоли Windows cp1251 при выводе Unicode
* **Симптом:** `UnicodeEncodeError: 'charmap' codec can't encode character...` при выводе через `print()` в консоль Windows.
* **Причина:** Стандартный вывод `sys.stdout` в Windows инициализирован кодовой страницей `cp1251`, которая не содержит символов международной диакритики и математических обозначений.
* **Решение:** Принудительная реконфигурация потоков ввода-вывода в начале скриптов:
```python
import sys

if sys.platform == 'win32':
    if hasattr(sys.stdout, 'reconfigure'):
        sys.stdout.reconfigure(encoding='utf-8')
    if hasattr(sys.stderr, 'reconfigure'):
        sys.stderr.reconfigure(encoding='utf-8')
```

### Проблема 13: Недопустимость смещения критериев гипотез post-hoc (Goalpost Moving)
* **Симптом:** Критерии успешности гипотезы корректируются после завершения расчетов под фактически полученные числа.
* **Причина:** Стремление объявить гипотезу подтвержденной вопреки экспериментальным фактам.
* **Решение:** Предикаты подтверждения/отклонения гипотез фиксируются до начала расчетов. Если рассчитанная величина выходит за установленные границы, гипотеза признается строго отклоненной.

### Проблема 17: Зависание консольных компиляторов LaTeX (MiKTeX) в интерактивном режиме
* **Симптом:** Процесс компиляции `pdflatex.exe`, `xelatex.exe` или `lualatex.exe` не завершается, вызывая исчерпание лимита времени (таймаут).
* **Причина:** При возникновении ошибок верстки, нехватке стилей или шрифтов MiKTeX переходит в интерактивный режим ожидания пользовательского ввода из стандартного потока `stdin` (символ приглашения `?`).
* **Решение:** Запуск компилятора обязан выполняться строго в неинтерактивном пакетном режиме с немедленным аварийным остановом при первой ошибке и квотированием путей:
```powershell
pdflatex -interaction=nonstopmode -halt-on-error "ИмяФайла.tex"
```
После завершения процесса проверяется код возврата `$LASTEXITCODE == 0`, а статус сборки верифицируется по строке `Output written on ...` в выходном потоке.

  3. Год издания и корректность наименования журнала.

### Проблема 21: Отсутствие утилит UNIX (head, tail, grep) в стандартной среде PowerShell на Windows
* **Симптом:** Ошибка оболочки `head : Имя "head" не распознано как имя командлета, функции...` (код возврата 1).

### Проблема 24: Ошибка десериализации чекпоинтов UnpicklingError в PyTorch 2.6+ при отсутствии weights_only=False
* **Симптом:** Исключение `_pickle.UnpicklingError: Weights only load failed... Unsupported global: GLOBAL pandas.core.frame.DataFrame...` при вызове `torch.load()`.
* **Причина:** Начиная с PyTorch 2.6, значение параметра по умолчанию изменено на `weights_only=True`. Это блокирует загрузку файлов `.pt`, содержащих структуры данных Python (`pandas.DataFrame`, `numpy.ndarray`, конфигурационные словари).
* **Решение:** При загрузке локальных доверенных чекпоинтов с метаданными экспериментов явно передавать `weights_only=False`:
```python
data = torch.load(path, map_location=device, weights_only=False)
```

### Проблема 25: Недопустимость использования синтетических генераторов (np.random.normal, гармоник) при построении иллюстраций
* **Симптом:** Графики вариограмм, профилей невязок и высот визуализируют вымышленные аналитические или стохастические кривые, не соответствующие расчетным матрицам.
* **Причина:** Использование псевдоданных в скриптах визуализации (`np.random.normal()`, `np.cos()`) вместо загрузки и индексации реальных тензоров.
* **Решение:** Код генерации графиков обязан загружать фактические файлы результатов (`.pt`, `.nc`) и извлекать точные сечения матриц и массивы лагов:
```python
h4_data = torch.load(h4_path, map_location='cpu', weights_only=False)
gamma_hat = np.array(h4_data['ftv_metrics']['gamma_hat'])
lags_m = np.array(h4_data['ftv_metrics']['lags_m'])
```

### Проблема 28: Фабрикация расчетных метрик и весовых файлов в отчетах (Ghost Metrics & Weights)
* **Симптом:** В аналитических журналах (`RESEARCH_NOTES.md`, `HYPOTHESES_AND_METHODS.md`) декларируются метрики (например, $L_{\text{test}} = 118.82$, $\operatorname{Var}(e) = 78.21$, эпоха 484), отсутствующие в валидированных JSON-файлах, и указываются несуществующие файлы весов (`.pt`).
* **Причина:** Внесение в документацию вымышленных чисел или теоретических ожиданий без фактического запуска оптимизационного процесса.
* **Решение:** Любая запись в отчет обязана верифицироваться чтением сгенерированного файла метрик на физическом диске с проверкой `os.path.getsize(weights_path) > 0`. Запрещается фиксировать результаты экспериментов без привязки к верифицируемому на диске артефакту.

### Проблема 31: cuSOLVER fallback при точном SVD на GPU для граничных и маскированных матриц в PyTorch
* **Симптом:** Предупреждение `UserWarning: torch.linalg.svd: During SVD computation with the selected cusolver driver, batches 0 failed to converge. A more accurate method will be used to compute the SVD as a fallback.` и резкое падение производительности вычисления (с 25 мс до сотен миллисекунд или секунд на матрицу).
* **Причина:** В драйвере CUDA cuSOLVER стандартный итерационный алгоритм Якоби `gesvdj` / `gesvda` не сходится на плохо обусловленных матрицах с резкими скачками ранга и большими областями нулевого дополнения (маскированная морская акватория или паддинг границ сцены). PyTorch переключается на точный QR-алгоритм `gesvd`.
* **Решение:** При обработке сплошной сцены с большим числом береговых тайлов для ускорения итерационных циклов IALM использовать Adaptive RSVD с динамическим рангом, либо при использовании точного SVD учитывать временной бюджет (~30 с на тайл с fallback).

### Проблема 32: Переполнение колонок c в таблицах LaTeX tabularx при длинных вердиктах
* **Симптом:** Сообщение компилятора `Overfull \hbox (...pt too wide) in alignment` и горизонтальный вылет текста таблицы за пределы страницы в скомпилированном PDF.
* **Причина:** Колоночный спецификатор `c` в LaTeX фиксирует центрирование без переноса строк. Если ячейка содержит многословный текст (например, формулировку вердикта по гипотезе), ширина колонки не ограничивается шириной страницы.
* **Решение:** Для текстовых колонок с переменной длиной использовать спецификаторы с явным ограничением ширины и переносом: `>{\centering\arraybackslash}p{<ширина>}` либо адаптивную колонку `>{\raggedright\arraybackslash}X`.

### Проблема 33: Рассинхронизация нумерации, порядка и графического содержания рисунков в статьях
* **Симптом:** Подпись к рисунку описывает графики, отсутствующие на изображении (например, подпись заявляет спектральную плотность мощности PSD или 2D карту теневой отмывки hillshade, а на рисунке изображены эмпирические полувариограммы или 1D профили высот и градиентов); порядок объявления рисунков в коде LaTeX нарушает сквозную нумерацию (Рис. 3 оказывается в коде раньше Рис. 1).
* **Причина:** Механическая вставка графических файлов без проверки фактических осей координат и заголовков подграфиков; перестановка параграфов текста без согласования порядка окружений `\begin{figure}`.
* **Решение:** При подготовке рукописи обязательно проверять фактическое графическое наполнение каждого PDF/PNG-файла иллюстрации. Подписи в LaTeX обязаны строго отражать действительное содержание осей координат. Окружения `\begin{figure}` должны размещаться в коде строго в порядке их первого упоминания в тексте (Рис. 1 $\to$ Рис. 2 $\to$ Рис. 3 $\to$ Рис. 4).

### Проблема 34: Ложное сопоставление путей при поиске по шаблонам имен (Aliasing fallback path in multi-subject dataset)

### Проблема 37: Взаимоисключающие соглашения координатных систем в открытых датасетах взгляда и позы головы (MPIIFaceGaze vs Columbia vs RT-GENE)
* **Симптом:** При объединении датасетов в мультидоменную выборку модель запоминает обучающих субъектов ($\mathcal{L}_{train} \to 2.6$), но на валидации застревает ($\mathcal{E}_{ang} \approx 11^\circ - 15^\circ$), а покомпонентная ошибка позы головы превышает $15^\circ - 24^\circ$.
* **Причина:** Несоответствие систем координат камер и знаков углов между датасетами:
  1. В канонической системе OpenCV ($X$ вправо, $Y$ вниз, $Z$ от камеры): при наклоне взгляда вниз $v_y > 0$, а тангаж $\theta = \arcsin(-v_y) < 0$.
  2. В сырых таблицах Columbia Gaze координата $Y$ была направлена вверх ($v_y < 0$ при взгляде вниз), из-за чего вычисление $\arcsin(-v_y)$ ошибочно давало положительный угол $+10^\circ$, прямо противоположный MPIIFaceGaze (расхождение $20^\circ$).
  3. В RT-GENE аннотация тангажа головы `head_pitch_rad` имела противоположный знак ($-17.14^\circ$) относительно вектора нормали лица `head_vec` ($v_y = -0.2947$, что соответствует $+17.14^\circ$), создавая внутреннее расхождение $34.28^\circ$.
* **Решение:** Программный контроль изоморфизма:
  1. Для Columbia Gaze вектор вычисляется строго из проверенных сферических углов:
     $$\mathbf{g} = [-\cos\theta \sin\phi, -\sin\theta, -\cos\theta \cos\phi]^T$$
  2. Для MPIIFaceGaze и RT-GENE углы и векторы вычисляются через согласованный метод `_normalize_vector_and_compute_angles`.
  3. Перед запуском обучения обязателен запуск теста верификации:
     $$\mathcal{E}_{ang}(\text{spherical\_angles\_to\_unit\_vector}(\theta, \phi), \mathbf{v}) \le 0.05^\circ$$
     на 100% строк каждого из трех датасетов.

### Проблема 38: Затухание градиентов косинусного лосса $1 - \cos\theta$ при малых угловых ошибках и доминирование классификационного Cross-Entropy
* **Симптом:** Модель сходится к валидационной ошибке $\approx 10.3^\circ$ и перестает улучшаться, несмотря на продолжение обучения. Кросс-энтропия по бинам классификации минимизируется, но целевая векторная ошибка не снижается.
* **Причина:** Косинусный лосс $\mathcal{L}_{cosine} = \lambda_{cos} (1 - \cos\theta)$ при малых ошибках $\theta \approx 10^\circ = 0.1745\text{ рад}$ аппроксимируется как $\lambda_{cos} \frac{\theta^2}{2}$. При $\lambda_{cos} = 2.0$ значение лосса равно всего $0.0304$, что составляет менее $0.15\%$ от общего составного лосса ($\approx 21.6$). Производная $\frac{d\mathcal{L}}{d\theta} = 2.0 \sin\theta \approx 0.35$ в радианах (соответствует $0.006$ на градус) на 2–3 порядка слабее градиентов кросс-энтропии ($\mathcal{L}_{CE} \approx 8.5$).
* **Решение:** Внедрение прямого углового лосса (Direct Angular Degree Loss) через $\arccos$ скалярного произведения векторов:
  $$\mathcal{L}_{ang} = \lambda_{ang} \cdot \frac{180}{\pi} \arccos\left(\text{clip}\left(\frac{\mathbf{g}_{gt} \cdot \hat{\mathbf{g}}}{\|\mathbf{g}_{gt}\|_2 \|\hat{\mathbf{g}}\|_2}, -1.0 + \epsilon, 1.0 - \epsilon\right)\right)$$
  При ошибке $10^\circ$ значение лосса равно $10.0$ (при $\lambda_{ang}=1.0$), что обеспечивает постоянный линейный градиент $\pm 1.0$ на каждый градус отклонения, направляя оптимизатор напрямую на минимизацию целевой метрики ВКР $\mathcal{E}_{ang} \le 5.20^\circ$.

### Проблема 39: Превышение лимита задержки CPU при использовании тяжелых бэкбонов (ResNet-18) и оптимизация через MobileNetV3 + ONNX Runtime
* **Симптом:** При использовании ResNet-18 время прямого прохода на CPU (4 потока) составляет $18.52 - 23.65\text{ мс}$ ($42 - 54\text{ FPS}$), что нарушает требование ТЗ ($T_{CPU} \le 8.0\text{ мс}$, конвейер $\ge 60\text{ FPS}$).
* **Причина:** Высокая вычислительная сложность ResNet-18 ($1.82\text{ GFLOPs}$ при стандартных $3 \times 3$ свертках с $11.2\text{M}$ параметров) и отсутствие специализированной векторизации под инструкции AVX2 / VNNI в PyTorch Eager.
* **Решение:**
  1. Переход на легковесные глубинные разделяемые свертки (Depthwise Separable Convolutions) архитектуры MobileNetV3-Large ($4.36\text{M}$ параметров).
  2. Экспорт модели в формат ONNX и выполнение инференса через `onnxruntime.InferenceSession` с параметром `intra_op_num_threads=4`.
  3. Результат: задержка прямого прохода на CPU снижена до **$4.47\text{ мс}$ ($223.7\text{ FPS}$)**, обеспечивая запас $44.1\%$ относительно норматива ТЗ ($\le 8.0\text{ мс}$).

### Проблема 40: Разрешение зрачка и подавление окулярных признаков макроструктурой лица при полнокадровом сверточном сжатии
* **Симптом:** Полнолицевая модель MobileNetV3-Large со слиянием признаков позы головы достигает $\mathcal{E}_{ang}^{val} = 8.47^\circ$ и застревает, демонстрируя расхождение лосса: $\mathcal{L}_{train} \to 2.74$, $\mathcal{L}_{val} \to 38.59$.
* **Причина:** При коэффициенте субдискретизации сверточного бэкбона $S = 32$ входное изображение лица $224 \times 224$ сжимается в карту признаков $7 \times 7$. Глазное яблоко, занимающее около $16 \times 32$ пикселей, проецируется менее чем в 1 ячейку карты признаков ($0.5 \times 1.0$). Оставшиеся 48 ячеек кодируют макропризнаки черепа, скул, овала лица и прически, провоцируя переобучение на идентификационных признаках обучающих субъектов в строгом Subject-Disjoint сплите.
* **Решение:** Разделение конвейера на два потока (Dual-Stream): полнолицевой поток для оценки ориентации черепа $(\theta_{head}, \phi_{head})$ и изолированный сиамский поток высокого разрешения ($64 \times 64$) для фрагментов глаз (Eye Crops), где 100% входных пикселей представляют радужку, лимб и зрачок, без вмешательства анатомической формы лица.

### Проблема 41: Сбой вывода Unicode-символов (∩, ±, ⊆) в стандартный вывод Windows с кодировкой CP1251
* **Симптом:** `UnicodeEncodeError: 'charmap' codec can't encode character '\u2229' in position ...: character maps to <undefined>`.
* **Причина:** В операционной системе Windows стандартный поток вывода консоли (`sys.stdout`) использует однобайтную кодовую страницу `cp1251` или `cp866`. Математические символы теории множеств (пересечение $\cap$, принадлежность $\in$, подмножество $\subseteq$) отсутствуют в таблице CP1251.
* **Решение:** В логах и консольных выводах заменять не-ASCII математические спецсимволы на эквивалентные текстовые ASCII-обозначения (`_inter_`, `in`, `subset`, `+/-`), либо перенастраивать кодировку `sys.stdout.reconfigure(encoding='utf-8')`.

### Проблема 42: Несоответствие оптической оси локального 2D-кропа детектора лица MTCNN и глобальной оптической оси камеры (эффект параллакса луча лица в RT-GENE)
* **Симптом:** Модель взгляда и позы лица, обучаясь одновременно на Columbia Gaze, MPIIFaceGaze и RT-GENE, на валидационных субъектах RT-GENE застревает с систематическим смещением (Bias) $-9.20^\circ$ по тангажу взгляда и $+12.31^\circ$ по тангажу головы, приводя к ошибке направления взгляда $14.99^\circ - 16.47^\circ$, в то время как на Columbia Gaze ошибка составляет $4.36^\circ$, а на MPIIFaceGaze $5.28^\circ$.
* **Причина:** В датасете RT-GENE сенсор Kinect v2 располагался на столе на расстоянии $1.9 \dots 2.2$ м и на высоте $0.22 \dots 0.25$ м ниже уровня глаз. Оптический луч из центра камеры к центру лица наклонен вверх на угол $\theta_{ray} = \arctan(t_y / t_z) \approx +11.5^\circ$. Кроп детектора лица MTCNN ($224 \times 224$) центрирует лицо, направляя локальную оптическую ось прямо в лицо. Однако в разметке датасета векторы взгляда и позы привязаны к глобальной оси камеры Kinect $[0, 0, 1]^T$. В локальном кропе взгляд в объектив соответствует тангажу $0^\circ$, а в глобальной системе камеры Kinect — тангажу $-11.5^\circ$. Модель, не зная трехмерного положения кропа в кадре, не способна скомпенсировать этот сдвиг на новых субъектах.
* **Решение:** Внедрение ортонормированной матрицы вращения $\mathbf{R}_{ray} \in SO(3)$ (Face Ray Normalization) на этапе загрузки данных в `DataUnifier.load_rtgene`. Векторы взгляда и позы головы RT-GENE преобразуются: $\mathbf{g}_{norm} = \mathbf{R}_{ray} \mathbf{g}_{cam}$, $\mathbf{h}_{norm} = \mathbf{R}_{ray} \mathbf{h}_{cam}$, совмещая глобальную ось камеры с оптическим лучом к центру лица без паразитного крена (нулевой roll). Невязка углов и векторов составляет $\mathcal{E}_{discrepancy} \le 0.028^\circ$ на 100% строк.

### Проблема 43: Ошибочное сопоставление неразмеченных изображений noglasses из вспомогательных GAN-сессий с метками glasses в RT-GENE
* **Симптом:** Модель сходится на 5 обучающих субъектах RT-GENE до ошибки $<0.5^\circ$, но на отложенных валидационном (`p009`, $11.61^\circ$) и тестовом (`p012`, $16.07^\circ$) субъектах дает ошибку свыше $11^\circ \dots 16^\circ$ и расхождение по позе головы $>20^\circ$. При этом та же самая модель на Columbia Gaze показывает ошибку $3.17^\circ$ (Val) и $4.82^\circ$ (Test), а на MPIIFaceGaze — $4.92^\circ$ (Val).
* **Причина:** Согласно официальной структуре RT-GENE (ECCV 2018, Zenodo 2529036) и `docs/05_datasets.md` (п. 1.7), датасет содержит два несинхронизированных типа сессий:
  1. `sXXX_glasses` ($114\,558$ размеченных кадров): участники носят очки-трекер SMI ETG 2W (60 Гц), формирующие истинную разметку `label_combined.txt`. Для обучения эти изображения обрабатывались нейросетью GAN, удаляющей очки (`inpainted/face`).
  2. `sXXX_noglasses` ($154\,755$ неразмеченных кадров): отдельная запись участников без очков, предназначенная исключительно для обучения CycleGAN. На этих кадрах аппаратный трекер взгляда отсутствовал.
  В локальном хранилище `DATA/rtgene_raw/` были загружены только архивы `_noglasses.tar`, а загрузчик `unification.py` производил сопоставление кадров `sXXX_noglasses` с метками `sXXX_glasses/label_combined.txt` по случайному совпадению сквозного целочисленного счетчика MTCNN `seq`. Модели навязывались случайные псевдо-метки, приводившие к переобучению на обучающих лицах и невозможности обобщения на отложенных субъектах.
* **Решение:** Исключение неразмеченных кадров `_noglasses` из обучающего контура. Использование только аппаратно верифицированных пар «изображение–метка» из архивов `_glasses.tar` (`inpainted/face`), либо обучение на мультидоменной выборке Columbia Gaze + MPIIFaceGaze ($43\,547$ верифицированных изображений).

### Проблема 44: Переполнение дискового пространства при массовой загрузке многогигабайтных tar-архивов и потоковая распаковка с автоочисткой
* **Симптом:** При попытке одновременного скачивания и распаковки всех архивов RT-GENE (34 tar-архива общим объемом $44.45\text{ ГБ}$) локальный диск $C:\$ переполнялся: хранение архива и распакованного дерева одновременно требует удвоенного пространства ($>80\text{ ГБ}$).
* **Причина:** Стандартный подход (сначала скачать все архивы, затем распаковать все) приводит к пиковому потреблению диска $\text{Size}_{\text{archives}} + \text{Size}_{\text{extracted}} \approx 30\text{ ГБ} + 25\text{ ГБ} = 55\text{ ГБ}$, что приводило к сбою ввода-вывода `No space left on device` или замедлению системы.
* **Решение:**
  1. Разделение загрузчика и распаковщика на параллельные асинхронные конвейеры.
  2. Запуск фонового процесса-наблюдателя (`watch_and_extract.py`), который каждые 10 секунд сканирует каталог `DATA/rtgene_raw/`. Как только очередной архив `sXXX_glasses.tar` заканчивает скачивание и проходит MD5-валидацию, процесс фильтрует и извлекает строго модальность `inpainted/face/*.png` (игнорируя полнокадровые фоновые сцены) и немедленно удаляет исходный `.tar` файл с диска.
  3. Результат: все 17 сессий RT-GENE ($114\,558$ чистых кадров) извлечены на 100%, при этом свободный объем диска $C:\$ остался на уровне $\ge 80.4\text{ ГБ}$ без единого пикового превышения лимитов.

### Проблема 45: Сигнатура аргументов GaussNoise в библиотеке Albumentations версии 2.0+ и несовместимость с устаревшим API var_limit
* **Симптом:** При вызове `albumentations.GaussNoise(var_limit=(10.0, 50.0))` возникает предупреждение `UserWarning: Argument(s) 'var_limit' are not valid for transform GaussNoise` и преобразование шума отбрасывается.

* **Решение:** В коде преобразований конвейера аугментации передавать `std_range=(0.02, 0.08)` (для нормализованных или целочисленных изображений с плавающей точкой) вместо `var_limit`.

### Проблема 46: Задержка срабатывания механизма раннего останова (Early Stopping) из-за жесткого порога минимальных эпох
* **Симптом:** Модель достигает минимальной ошибки на 2-й эпохе, после чего на протяжении 20 эпох ошибка валидации непрерывно растет (переобучение), однако ранний останов не срабатывает и обучение продолжается вхолостую.
* **Причина:** В классе `EarlyStopping` параметр `min_epochs` по умолчанию имел жесткое значение $30$, блокируя инкремент счетчика `self.counter` до наступления 30-й эпохи вне зависимости от темпов роста ошибки валидации.
* **Решение:** Инициализировать `EarlyStopping` с параметром `min_epochs = 0`, обеспечивая безусловный инкремент счетчика терпения (`patience`) с первой же эпохи при отсутствии улучшения целевой валидационной метрики.

### Проблема 47: Квантование системного таймера time.monotonic() в Windows (квант 15.625 мс) и искажение телеметрии задержек
* **Симптом:** При замере задержек прямого прохода нейросети (Forward pass) и сквозного конвейера телеметрия фиксирует дискретные скачки $0.0\text{ мс}$, $15.6\text{ мс}$, $31.2\text{ мс}$, $46.9\text{ мс}$, искажая реальные показатели производительности.
* **Причина:** В операционной системе Windows стандартный таймер `time.monotonic()` опирается на вызов `GetTickCount64()`, частота обновления которого привязана к стандартному кванту прерываний системных часов (System Timer Quantum: $64\text{ Гц} \implies 15.625\text{ мс}$).
* **Решение:** Для всех высокоточных замеров миллисекундных и микросекундных задержек в конвейере трекинга использовать строго `time.perf_counter()`, использующий системный счетчик `QueryPerformanceCounter` с наносекундным разрешением:
```python
t_start = time.perf_counter()
# ... вычисления / прямой проход ...
latency_ms = (time.perf_counter() - t_start) * 1000.0
```

### Проблема 48: Виртуализация координат курсора мыши и искажение экранного разрешения в ОС Windows при отсутствии флага DPI-Awareness
* **Симптом:** Физическое разрешение дисплея пользователя составляет $2880 \times 1800$, однако вызовы `GetSystemMetrics` возвращают виртуализированное масштабированное разрешение (например, $1920 \times 1200$ при DPI-масштабе 150%), а позиционирование курсора через `SetCursorPos` смещается относительно физических пикселей экрана.
* **Причина:** По умолчанию процессы Windows без манифеста считаются системой DPI-Unaware. Менеджер окон DWM виртуализирует координаты для совместимости со старыми приложениями.
* **Решение:** Принудительное включение флага осведомленности о DPI до вызова любых Win32-функций и до создания окон OpenCV:
```python
import ctypes
try:
    ctypes.windll.user32.SetProcessDPIAware()
except Exception:
    pass
screen_w = int(ctypes.windll.user32.GetSystemMetrics(0))
screen_h = int(ctypes.windll.user32.GetSystemMetrics(1))
```

### Проблема 54: Несоответствие физической сетки координат и логической системы координат Qt при масштабировании дисплея 175%
* **Симптом:** Точки калибровки и эталонного бенчмарка (в частности, точки в правых столбцах и нижних строках сетки) выходят за пределы видимой области окна. На экране видна только левая верхняя часть сетки.
* **Причина:** Физическое разрешение дисплея составляет $2880 \times 1800$ пикселей. При системном масштабировании Windows $175\%$ (`devicePixelRatio = 1.75`) логический размер окна и экрана в Qt составляет:
  $$W_{\text{logical}} = \frac{2880}{1.75} = 1645.7 \approx 1646\text{ px}, \quad H_{\text{logical}} = \frac{1800}{1.75} = 1028.6 \approx 1029\text{ px}$$
  Генератор тестовых точек формировал координаты в абсолютных физических пикселях ($X \in [345.6, 2534.4]$, $Y \in [324.0, 1548.0]$). Отрисовка без деления на физическое разрешение приводила к передаче физических пикселей в логический холст Qt: точка с координатой $X = 2534.4$ отображалась в логической позиции $2534.4$, что на $888.4\text{ px}$ правее правой границы окна ($1646\text{ px}$).
* **Решение:** Внедрение нормализованного масштабирования координат через константное физическое разрешение дисплея:
  $$W_{\text{ref}} = 2880.0\text{ px}, \quad H_{\text{ref}} = 1800.0\text{ px}$$
  Отрисовка на холсте `QPainter` вычисляется по формулам:
  $$X_{\text{draw}} = \frac{X_{\text{phys}}}{W_{\text{ref}}} \cdot W_{\text{widget}}, \quad Y_{\text{draw}} = \frac{Y_{\text{phys}}}{H_{\text{ref}}} \cdot H_{\text{widget}}$$
  В логическом окне $1646 \times 1029$:
  $$X_{\text{draw}}(\text{Point 3}) = \frac{2534.4}{2880.0} \cdot 1646 = 0.88 \cdot 1646 = 1448.48\text{ px} \quad (\text{отступ от правого края: } 197.52\text{ px})$$
  $$X_{\text{draw}}(\text{Far Right}) = \frac{2707.2}{2880.0} \cdot 1646 = 0.94 \cdot 1646 = 1547.24\text{ px} \quad (\text{отступ от правого края: } 98.76\text{ px})$$
  Все 13 точек бенчмарка и 9 точек калибровки гарантированно размещаются внутри видимого прямоугольника виджета.

### Проблема 55: Вертикальная инверсия экранного вектора и курсора из-за несоответствия знака угла тангажа (Pitch)
* **Симптом:** При взгляде вниз курсор и стрелка вектора взгляда смещаются вверх к верхней границе экрана; при взгляде вверх смещаются вниз.
* **Причина:** В датасете MPIIFaceGaze и канонической модели L2CS координата взгляда $Y$ на экране отсчитывается сверху вниз (экранная система координат: $(0, 0)$ в левом верхнем углу, ось $Y$ направлена вниз). Угол тангажа $\theta$ (Pitch) положителен при взгляде вверх и отрицателен при взгляде вниз:
  $$\text{Corr}(\theta_{\text{deg}}, Y_{\text{screen\_px}}) = -0.7345$$
  Исходная формула содержала положительный знак: $dy = +\text{gain}_y \cdot d \cdot \tan(\theta - \theta_0)$. При взгляде вниз ($\theta < \theta_0$) разность $(\theta - \theta_0)$ отрицательна, что давало отрицательное смещение $dy < 0$ (перемещение к верхней границе $Y = 0$).
* **Решение:** Фиксация отрицательного знака в уравнении геометрической проекции:
  $$dx_{\text{mm}} = \text{gain}_x \cdot d \cdot \tan(\phi)$$
  $$dy_{\text{mm}} = -\text{gain}_y \cdot d \cdot \tan(\theta - \theta_0)$$
  где $d = 600.0\text{ мм}$ (дистанция от глаз до плоскости монитора), $\theta_0 = -5.5^\circ$ (базовый угол наклона головы относительно оптической оси камеры), $\text{gain}_x = 1.85$, $\text{gain}_y = 1.65$.
  При взгляде вниз ($\theta < \theta_0$):
  $$\theta - \theta_0 < 0 \implies \tan(\theta - \theta_0) < 0 \implies dy_{\text{mm}} = -\text{gain}_y \cdot d \cdot (-|\dots|) > 0 \implies Y_{\text{screen}} \text{ увеличивается (движение вниз)}.$$
  Для графической отрисовки вектора взгляда стрелка вычисляется как:
  $$dx = L \cdot \sin(\phi), \quad dy = -L \cdot \sin(\theta - \theta_0)$$
  где $L = 80\text{ px}$ — длина направляющего отрезка. Вектор строго совпадает с физическим направлением взгляда.

### Проблема 57: Исключение IR Graph при JIT/ONNX трассировке динамических координатных сеток torch.meshgrid
* **Симптом:** В модуле `measure_forward_latency` при выполнении `torch.jit.trace` или `torch.onnx.export` генерируется исключение с дампом IR Graph на сотни строк.
* **Причина:** В архитектуре с динамическими размерами признаковых карт и генерацией координатных сеток через `torch.meshgrid(indexing="ij")` трассировщик PyTorch JIT пытается статически захватить буферы `grid_x` и `grid_y`. Это обеспечивает сохранение непрерывности конвейера обучения без аварийного завершения.

### Проблема 58: Коллинеарное подавление чувствительности взгляда (Pitch) при 9-точечной сеточной калибровке
* **Симптом:** При калибровке модели на 9 статических точках сетки траектория кругового слежения `CircleTrajectory` на тесте сжимается по вертикали в узкую линию ($Y_{\text{range}} \approx 500\text{ px}$ при истинном диаметре $1152\text{ px}$), а вертикальная корреляция падает с $R_y = 0.85$ до $0.30$.
* **Причина:** Пользователь при фиксации на нижних точках сетки (строка 3, $Y = 1548\text{ px}$) наклоняет голову вниз ($head\_pitch$ увеличивается с $+7.75^\circ$ до $+23.45^\circ$, $\Delta = +15.70^\circ$). При регрессии по 5 некоррелированным параметрам ($1, yaw, pitch, head\_yaw, head\_pitch$) на малом числе точек ($N = 9$) матрица $X^T X$ становится плохо обусловленной: $head\_pitch$ забирает на себя практически весь наклон ($w_{hp} = +37.1\text{ px/deg}$), а вес собственного взгляда $pitch$ зажимается до нефизических значений $w_{pitch} = -7.2\text{ px/deg}$ (при физическом оптическом коэффициенте $100.0\text{ px/deg}$). При последующем плавном круговом движении глаза двигаются независимо от головы, но из-за заниженного веса $w_{pitch}$ вертикальный отклик курсора уменьшается в 5.6 раз.
* **Решение:** 
  1. Внедрение раздельной ортогональной калибровки (Decoupled Orthogonal Calibration): ось $X$ аппроксимируется строго по $[1, yaw, head\_yaw]$, ось $Y$ — по $[1, pitch, head\_pitch]$ с нулевыми перекрестными коэффициентами.
  2. Включение всех 13 статических фаз фиксации (`StaticFixation`, включая граничные точки верхнего и нижнего краев экрана: `Far Top Edge` $Y = 252\text{ px}$ и `Far Bottom Edge` $Y = 1602\text{ px}$) с регуляризацией $\lambda = 1.0$. Вес $w_{pitch}$ восстанавливается до $-45.5\text{ px/deg}$, медианная ошибка угла падает до $3.14^\circ$, а корреляция $R_y$ достигает $0.804$.

### Проблема 60: Исключение AttributeError: ptp was removed from ndarray class в NumPy 2.x
* **Симптом:** При вызове метода массива `arr.ptp()` в Python-скриптах с установленным NumPy 2.0+ генерируется исключение:
  `AttributeError: ptp was removed from the ndarray class in NumPy 2.0. Use np.ptp(arr, ...) instead.`
* **Причина:** В мажорном обновлении NumPy 2.0 метод экземпляра `ndarray.ptp()` был окончательно удален из C-API и интерфейса массива. Допустимым остался только функциональный интерфейс модуля `numpy.ptp(arr)`.
* **Решение:** Замена всех вызовов `arr.ptp()` на синтаксически совместимую функцию верхнего уровня `np.ptp(arr)` во всех вспомогательных скриптах и модулях оценки.
